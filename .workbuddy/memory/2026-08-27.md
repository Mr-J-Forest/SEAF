## 修复 AMP 梯度溢出导致 screen 队列全军覆没的问题

背景（来自 codex 会话 01a03ea9）：`d99c0c62ecf7_oras5_recent_screen_fast_v1` 队列中 4 个模型（TSC-Fusion/FourCastNet/ClimaX/Swin）全部因 `FloatingPointError: 梯度范数非有限: inf` 中止。根因是 train.py 硬编码 fp16 autocast + 梯度范数 inf 立即抛错，瞬时 fp16 反向溢出（GradScaler 本应跳步并降 scale）杀死了整个实验。

修复（提交 `dae1abf` + 类默认补充提交）：
- 新增 `mixed_precision_dtype`（默认 auto：bf16 优先，回退 fp16），GradScaler 仅在 fp16 时启用
- 梯度非有限但损失/输出有限时按 AMP 标准语义跳步，连续超过 `nonfinite_grad_skip_limit`（默认 30）才判发散；损失/输出非有限仍立即失败
- 溢出计数持久化到 checkpoint，dtype 与跳步统计写入 run_summary
- 新增 tests/test_amp_overflow_handling.py；服务器上 88 项测试全部通过

执行与重启：
- 同步到 westb 服务器（connect.westb.seetacloud.com:42977，RTX 4090，bf16 已验证支持）
- 新 campaign：`86a4b6022f_oras5_recent_screen_fast_v2`（baseline，max-parallel 2）+ `86a4b6022f_oras5_ablation_screen_fast_v2`（watcher 自动接续）
- 验证：TSC-Fusion epoch 1-2 正常（val 0.8688→0.8392），FourCastNet epoch 1 正常（此前在 epoch 3 崩溃）

注意：本地 Windows 无可用的 torch 环境（.venv 是 Linux venv，WSL 被安全策略禁用），测试在服务器上运行。

## 修复 bf16 eval 导出崩溃 + 评估缺样本索引（两个纯评估路径 bug）

baseline 队列 `86a4b6022f_oras5_recent_screen_fast_v2` 训练全部完成（早停后保存 best_model.pth），但 TSC-Fusion 之外的 3 个模型在「训练后评估导出」阶段崩溃，导致队列把整组标 FAILED（无 evaluation.json / _SUCCESS）。TSC-Fusion 因输出恰好是 float32 逃过一劫（队列标 _SUCCESS）。

两个根因（都已修，提交 `5482005` + `cf7e19a`，git commit `cf7e19a`，synced 05:42Z，新 training_source_hash=`e6829e85f5…`）：
- `train.py evaluate()` 收集预测时 `outputs.cpu().numpy()`：bf16 autocast 下模型输出是 bfloat16，NumPy 不支持该标量类型 `.numpy()` → `TypeError: Got unsupported ScalarType BFloat16`。改 `outputs.float().cpu().numpy()` / `targets.float()...`（与精度无关，纯数值导出）。
- `data_loader.py` 的 `return_sample_index` 之前只在 GTB 分支置 True；非 GTB 模型（FCN/ClimaX/Swin）返回 2-tuple，使 `evaluate()` 的 `sample_indices` 为空 → `预测样本与 sample_indices 数量不一致：3344 != 0`。改为 train/val/test 一律 True。

## 新增 `scripts/eval_best_only.py` 逃生舱

当 bug 纯在评估/导出路径（训练数值不变）时，已训好的 best_model.pth 仍有效。该脚本用 `train.py` 的 `OceanModelTrainer.evaluate` 给冻结权重重算指标，刻意绕过 `load_checkpoint` 的跨版本 hash 闸门（`_load_best_model_weights` 只加载 model_state_dict）。
用法：`.venv/bin/python -u scripts/eval_best_only.py --config configs/experiments/<exp>.json --result_dir <campaign>/screen/<run>/seed_42 --split validation`
- FCN 经此重算成功（RMSE 0.8669 / MAE 0.5056 / R² 0.4575）。
- ClimaX / Swin 首次跑被 OOM 杀（与正在跑的 ablation 训练争夺 ~90GiB cgroup）。

## ablation 因 source-hash 闸门无法原样续跑 → 改用全新 campaign

为给 ClimaX/Swin 重算腾内存，我暂停了 ablation 队列（kill watcher+训练进程），重算完再想续跑时失败：
`RuntimeError: campaign '86a4b6022f_oras5_ablation_screen_fast_v2' belongs to a different source hash`
原因：该 ablation campaign 是 baseline watcher 在同步 eval 修复**之前**自动拉起的，记录的 training_source_hash=86a4b6022f（旧代码，eval 有同样的崩溃）；当前代码已含修复（hash e6829e85f5…）。闸门正确拦截了「混用协议」续跑——旧代码跑 ablation 也会在自己评估时崩。

处置：放弃旧 ablation 续跑，改用修复后代码全新 campaign `e6829e85f5_oras5_ablation_screen_fast_v2`（11 个实验，max-parallel 2）重跑。因训练数值与修复无关，旧 ablation 的已训权重本可复用，但闸门无法干净 resume，且唯一可复用进度（no_tendency ~18min）可忽略，故干净重跑最稳。旧 `86a4b6022f_…_ablation_…` 目录沦为孤儿，留作参考。

经验：改了训练相关文件（train.py/data_loader.py）后 training_source_hash 会变 → 旧 campaign 一律无法 resume；需新 campaign。eval_best_only 重算前务必先停掉其它占内存的训练，否则 OOM。
